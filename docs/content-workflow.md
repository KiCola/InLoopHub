# 内容工作流

从想法到发布的状态流转，依据任务书 §17。状态的合法取值定义在 Front Matter 里。

```text
idea ─▶ researching ─▶ draft ─▶ review ─▶ ready ─▶ published
```

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `idea` | 只有选题 | 想写，但还没开始查资料 |
| `researching` | 查资料、读论文/源码 | 开始收集素材 |
| `draft` | 已成文初稿 | 结构与正文成形，允许有明显缺口 |
| `review` | 自审中 | 内容完整，在改措辞、补图、校数据 |
| `ready` | 可发布 | 已通过检查，产物可交付 |
| `published` | 已发布 | 已在公众号上线 |

## 两条操作纪律

1. **状态只在相邻之间移动。** 不要从 `idea` 直接跳 `ready`——跳过的中间状态通常意味着
   跳过了"自审"这一步，而发布事故基本都出在这里。
2. **`ready` 之前必须跑一次发布前检查。** 使用面板按钮或 `inloop check <文章> --publish`，
   检查属性、图片路径/格式/体积和正文转换提示，再完成人工复核。
   普通 `check` 仅做属性校验。程序不会因检查通过而自动改变写作状态。

## 关于修改状态

系统提供按文章路径修改状态的命令（任务书 §17 的 `inloop status <article> <new-status>`），
该命令已实现。可直接编辑 `<内容目录>/<年份>/<slug>/index.md` 的 Front Matter，
或用 `inloop status <slug> <状态>`、面板状态下拉修改（只改 status 一行）。
这是**唯一**允许改动已存在文章文件的场景，且改动范围仅限 `status` 一行。

## 分支策略

任务书 §24 建议的对应关系：

| 分支 | 用途 |
|---|---|
| `main` | 内容已稳定 |
| `draft/<slug>` | 一篇文章的写作过程 |
| `feature/*` | 功能开发 |

把 `main` 视作"内容已稳定"的标记，是这套流程里最省事的做法：
文章写完、检查通过，再合入 `main`。
